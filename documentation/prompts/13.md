# PR-13

## Purpose

Quarantine the flaky test `tests/test_harness.py::test_device_cpu_is_slower`
in CI. It failed once on the `windows-latest` job after #11 was merged (the
device took 0.10 s against 0.11 s unrestricted, so the CPU cap had no effect)
and passed when the same commit was re-run. On a local machine it is reliable:
the device is 8–10 times slower (0.93–1.19 s against 0.12 s).

Following the course material, the flaky test is disabled where it is flaky
and fixing it is recorded as a to-do in issue #12. The test still runs locally.

This PR changes only `tests/test_harness.py`.

## Prompts

The code was generated with Claude Code (model: Claude Opus 5.5).

### Prompt 1

> CI failed on main after merging #11: `test_device_cpu_is_slower` failed on
> windows-latest with `assert 0.1 > (3 * 0.11)`. Why, and is it caused by our
> webedge or benchmark changes?

### Results 1

The LLM showed that every webedge, benchmark and sensor test passed on both
Windows and Linux; only the harness CPU test failed. It ran the same probe
three times locally, where the device was 8–10 times slower, so the cap works
on a normal machine.

Its first explanation, that GitHub's own Job Object stops the nested CPU cap
from working on its Windows runners, was **rejected**: re-running the failed
job on the same kind of runner passed. The test is therefore flaky, not
broken. The more likely cause is that the probe only lasts about 0.1 s, and on
shared, virtualised runners the cap does not always take effect within that
time. This matches the existing comment in `ci.yml` that shared CI machines
give unreliable timings.

### Prompt 2

> Henri suggested that, per the course material, we should disable the flaky
> test and mark fixing it as a to-do. I opened issue #12 for it. Make the
> change.

### Results 2

The LLM added a second `skipif` that skips the test when `CI=true`, which
GitHub Actions sets, with the reason `flaky on shared CI runners, see #12`.
A comment above it explains why and links the issue.

Review findings:

- **Accepted: skip only in CI, not everywhere.** The test is reliable locally,
  so it keeps checking the CPU cap there. In CI the skip and its reason appear
  in the pytest output, so the quarantine stays visible.
- **Not done here: the real fix.** Making the probe longer, or measuring CPU
  time instead of wall-clock time, is left to #12. There is no time to verify
  such a fix properly before the course deadline.

Verified both ways: locally all 8 harness tests passed; with `CI=true`,
7 passed and this test was skipped with the expected reason.

Remaining risk: while quarantined, a real regression in the Windows CPU cap
would not be caught by CI, only by running the tests locally.

### Prompt 3

> hekazu asked in review: "Is it possible to identify the CI type to still run
> the test on the functioning Linux CI?" Make that change.

### Results 3

The LLM narrowed the skip to `CI=true` **and** Windows
(`sys.platform == "win32"`), and changed the reason to
`flaky on shared Windows CI runners, see #12`. Only Windows CI failed, so
Linux CI should keep the check.

Review finding: on Linux the test also has its original skip, which applies
when `systemd-run --user` is unavailable, because there is no CPU cap without
it. `ci.yml` notes that this is expected on GitHub's Linux runners, so the test
may still be skipped there for that reason. That is a separate, older skip and
is left unchanged.

Verified: locally all 8 harness tests passed; with `CI=true` on Windows the
test was skipped with the new reason; the condition is false on Linux.
