# PR-6

## Purpose

Create a simple Python webedge component for the project.

The webedge is a separate component that receives HTTP requests on one address and forwards them to a configurable target address. It should not share code with the existing sensor infrastructure or harness.

The implementation should remain small and use Python standard-library modules where possible.

## Meeting – 29 September 2026

During the group meeting, the webedge task was discussed and clarified.

The project leader explained that the webedge should:

* be a separate component from the sensor infrastructure;
* receive requests on one address and forward them to another address;
* use a configurable target;
* later be able to target either an unrestricted sensor or the project harness;
* return the target response to the original client;
* remain simple and not share code with the sensor infrastructure.

Based on the meeting discussion, the implementation was kept as a small Python HTTP forwarding component. No RSA, ML-KEM, Docker, database, authentication, or other additional functionality was added at this stage.

## RSA Requirement Update – 30 September 2026

During the follow-up discussion, the project leader clarified that the webedge must also use RSA encryption for communication with the client.

The required flow is:

* Client → Webedge: RSA encrypted
* Webedge → Sensor: normal HTTP
* Sensor → Webedge: normal HTTP
* Webedge → Client: RSA encrypted

The existing webedge was therefore updated to add RSA encryption while keeping the sensor connection as normal HTTP.

### RSA Implementation

The updated implementation:

* uses the `cryptography` library with RSA-OAEP;
* generates a Webedge RSA key pair;
* uses the Webedge public key to encrypt client requests;
* uses the Webedge private key to decrypt client requests;
* receives the client's public key with the request;
* uses the client's public key to encrypt responses;
* allows the client to decrypt responses with its private key;
* keeps the Webedge-to-sensor connection as normal HTTP;
* rejects requests that are not properly RSA encrypted;
* keeps the existing configurable target host and port.

No ML-KEM, Docker, database, authentication, or other unrelated functionality was added.
