# PR-6

## Purpose

Create a simple Python webedge component for the project.

The webedge is a separate component that receives HTTP requests on one address and forwards them to a configurable target address. It should not share code with the existing sensor infrastructure or harness.

The implementation should remain small and use Python standard-library modules where possible.

## Meeting – 29 September 2026

During the group meeting, the webedge task was discussed and clarified.

The project leader explained that the webedge should:

* be a separate component from the sensor infrastructure;
* receive requests on one address and forward them to another address;
* use a configurable target;
* later be able to target either an unrestricted sensor or the project harness;
* return the target response to the original client;
* remain simple and not share code with the sensor infrastructure.

Based on the meeting discussion, the implementation was kept as a small Python HTTP forwarding component. No RSA, ML-KEM, Docker, database, authentication, or other additional functionality was added at this stage.

I am working on a university group project where we are modernizing a small legacy edge-cloud system.

My task is to create a simple Python component called a webedge.

The requirements I have been given are:

* Prefer Python standard-library modules so that no new dependencies are needed unless they are really necessary.
* Add simple tests for the main webedge functionality.

Please suggest:

1. A simple file structure.
2. The Python implementation.
3. Basic tests.
4. How I can run the webedge and tests using the existing Poetry setup.
5. A short explanation of how the request moves through the webedge.
6. Any important issues that I should check when reviewing the generated code.

Please do not add unnecessary features or dependencies. Keep the solution small and suitable for this university project.

### Results 1

The initial generated implementation provided a simple Python webedge using the standard library.

It received HTTP GET requests and forwarded them to a configurable target using `WEBEDGE_TARGET_HOST` and `WEBEDGE_TARGET_PORT`.

The initial tests checked that the target response was returned and that a request to `/test` received a successful response.

The initial implementation and tests were then reviewed. The review identified that the path-preservation test did not actually verify which path the target received.

### Results 2

The review found that the path-preservation test needed to be improved.

The target test server was changed to record the path received from the webedge. The test then explicitly checks that `/test` was received by the target.

The HTTP error handling was also improved by handling `HTTPError` separately from `URLError`.

The revised tests were run with:
