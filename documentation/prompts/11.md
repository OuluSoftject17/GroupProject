# PR-11

## Purpose

Benchmark the RSA and ML-KEM key exchange in `webedge.py`. The project brief
asks for baseline measurements and an evaluation of performance, and until
now we had no numbers to show what the move to ML-KEM costs or saves.

The benchmark times the cryptography of one request on the client and on the
webedge, key generation, and the bytes sent per request. It can also time
whole HTTP requests through a local webedge and sensor. Every run saves a
Markdown report to `benchmark-results/`.

This PR builds on PR #9 (`pypaa/webedge-mlkem`). It adds
`benchmark_webedge.py` and `test_benchmark_webedge.py`, and changes
`.gitignore`.

> Optionally run the same script inside our limited-hardware simulation as

### Results 1

The LLM produced `benchmark_webedge.py` and a smoke test. The script calls
`webedge.py`'s own `encrypt`, `decrypt`, `derive_key`, `aead_encrypt` and
`aead_decrypt`, and repeats the steps of `open_rsa_request` and
`open_mlkem_request`. Each request is split into four steps (client encrypts
request, webedge opens it, webedge encrypts response, client decrypts it) plus
the whole request. Key generation is timed separately with fewer runs, since
one RSA-2048 key takes about 30 ms. `--http` also times whole requests on
localhost.

Review findings:

- **Accepted:** garbage collection is turned off while timing, so a GC pause
  does not show up as a crypto outlier. Message sizes are measured from real
  output, not hard-coded.
- **Checked for fairness:** the ML-KEM client step includes Base64-encoding
  the KEM ciphertext, because a new one is sent with every request. The RSA
  client's key header is its fixed public key and is encoded once. This is
  explained in a code comment.
- **Fixed:** `--http` changed `webedge.TARGET_HOST` and `TARGET_PORT` and did
  not change them back, which could affect other tests in the same pytest run.
  They are now restored.
- **Rejected: running inside the harness.** The harness simulates the sensor,
  not the webedge, and its module allowlist blocks `hashlib` and `ssl`, so
  `cryptography` cannot even load there. For constrained hardware the report
  cites published benchmarks instead (wolfSSL on STM32, ML-KEM on RP2040).
- **Not added to CI:** CI only runs `pytest` on pull requests and pushes to
  `main`, and leaves timing out on purpose because shared runners give
  unreliable numbers. CI therefore runs only the smoke test, which proves the
  script still works. The real benchmark is run locally.

All tests passed (44 passed, 1 skipped).

### Prompt 2

> Can you make it so that it exports a report every time we run it? I want

### Results 2

Every run now saves its report as
`benchmark-results/webedge-benchmark-<date>_<time>.md`, or to `--output-dir`.
The file is opened in `"x"` mode, so a run never overwrites an earlier one.
The tests write to a temporary directory. `benchmark-results/` is ignored in
git; the run a report cites is added with `git add -f`.

Review findings:

- **Fixed:** the first version had a broken string literal (`"\n"` split over
  two lines), so the module failed to import. The test run caught it.
- **Modified:** the run time used `%Z`, which on Windows prints a name such as
  "FLE Daylight Time". It now prints a numeric offset, for example
  `UTC+0300`.

All tests passed (46 passed, 1 skipped). A full run with `--http` (2,000 runs,
Python 3.14.6, cryptography 50.0.2, OpenSSL 4.0.3, Windows 11):

| Per request (median) | RSA-2048 | ML-KEM-768 |
| --- | ---: | ---: |
| Cryptography, whole request | 0.439 ms | 0.106 ms |
| Webedge opens request | 0.196 ms | 0.061 ms |
| Client encrypts request | 0.019 ms | 0.042 ms |
| Key generation | 31.5 ms | 0.13 ms |
| Whole HTTP request (localhost) | 1.99 ms | 1.50 ms |
| Bytes sent | 904 | 1,562 |

ML-KEM is about 4 times faster for the cryptography of a whole request and
slower only when the client encrypts a request. Its cost is size: the
1,452-byte KEM header makes a request 1.73 times larger.

Remaining risks: the numbers come from one Windows machine with CPU scheduling
not controlled, they include Python overhead, and RSA-2048 and ML-KEM-768 do
not have the same security level. They show the trade-off in our code, not a
general ranking of the algorithms.
