# PR-2

## Purpose

Add a test harness around the legacy sauna sensor (`sensor.py`) so its current
behaviour is pinned down before the system is modernised with ML-KEM. The
harness starts the sensor on a free port, talks to it through a small HTTP
client, injects network faults between the client and the sensor, and records a
performance baseline. `sensor.py` and the existing unit tests are unchanged.

What was added:

* `harness/process.py`: starts the sensor on a free localhost port, waits
  until `/health` answers, and always stops it afterwards. Works on Windows.
* `harness/client.py`: a standard-library HTTP client behind a `Transport`
  interface, so an ML-KEM transport can be added later. If
  `HARNESS_TARGET_URL` is set, the tests use that sensor instead of starting
  one.
* `harness/faults.py`: a proxy that can add delay, drop the connection, return
  a 500, return invalid JSON, or send the response very slowly.
* `harness/baseline.py`: records latency (p50/p95/p99), errors, response size
  and requests per second, plus the Python version, OS and git commit.
* `tests/characterization/`: tests that pin the sensor's current behaviour.
  Behaviour that looks wrong is tested as-is and marked
  `# CHARACTERIZATION: possibly a bug`.
* `tests/resilience/`: tests showing that the client fails cleanly and never
  hangs when the connection misbehaves.
* `tests/selftest/`: tests for the harness itself.
* `harness/README.md`: run commands and a "Known limitations and risks"
  section.
* `pyproject.toml`: pytest added as a Poetry dev dependency, pytest settings,
  and `package-mode = false`. Without that setting, `poetry install` fails
  because the repository is not an installable package.

### Prompt 1

This repo contains a legacy simulated sauna sensor (sensor.py) with an HTTP API and unit tests (test_sensor.py). Build a test harness around it. Do not implement cryptography, a gateway, or a cloud service. Do not rewrite sensor.py.

Then build:
- harness/process.py: start sensor.py on a free port, poll /health until ready (no fixed sleeps), always stop it afterwards. Must work on Windows too.
- harness/client.py: a small stdlib HTTP client behind a Transport interface, with a plain-HTTP implementation only. An ML-KEM transport will be added later. If HARNESS_TARGET_URL is set, use it instead of starting the sensor.
- tests/characterization/: pin current behaviour (fields, types, status codes, states, ranges, gradual changes). Assert properties, not exact random values. If current behaviour looks wrong, test it as-is and mark it with a "# CHARACTERIZATION: possibly a bug" comment.
- harness/faults.py + tests/resilience/: a proxy between the client and the sensor that can add delay, drop the connection, return a 500, or return invalid JSON. Tests show the client fails cleanly and never hangs.
- harness/baseline.py: `python -m harness.baseline --duration 30 --out baseline.json`. Record latency p50/p95/p99, errors, response size and requests/sec, plus Python version, OS and git commit. Exclude a short warm-up.

Rules:
- Use pytest as a Poetry dev dependency. The existing unittest tests must still pass unchanged.
- `poetry run pytest -m "not slow"` must finish in under 60 seconds.
- No hard-coded ports. Localhost only.
- Add harness/README.md with the run commands.

Finish with a "Known limitations and risks" section: what isn't tested, what might be flaky, and what assumptions I should verify.

### Results 1

The LLM generated the files listed under Purpose. It ran the tests locally on
Windows 11 with Python 3.14:

* `poetry run pytest -m "not slow"`: 300 passed in about 25 seconds.
* `poetry run pytest -m slow`: 3 passed in about 93 seconds.
* `python -m unittest test_sensor`: the original 10 tests still pass.
* The characterization and resilience tests also pass against a separately
  started sensor through `HARNESS_TARGET_URL`.
* `python -m harness.baseline --duration 30 --out baseline.json` completed
  with 0 errors, a p50 latency of about 15 ms, and about 76 requests per
  second.

The characterization tests found these behaviours, now marked
`# CHARACTERIZATION: possibly a bug`, for the group to decide on:

* The HTTP API cannot change the sauna state, so over HTTP the sensor always
  reports a cold sauna (about 22 °C).
* Adding a query string, such as `/measurements?x=1`, returns 404.
* `HEAD` requests return 501.
* One client that connects and sends nothing blocks every other client,
  because the server is single-threaded and has no timeout.
* All servers in one process share a single sensor object.
* `python sensor.py` always uses port 8000, with no way to change it.
* Temperature changes are limited to 5 per step, but humidity changes are not
  limited.

Untested areas, possible sources of flaky tests, and assumptions to verify are
listed in `harness/README.md` under "Known limitations and risks".
