# PR-3

## Purpose

Add a harness that simulates the constrained device the legacy sauna sensor
runs on, following the harness goals from meeting 3 (2026-09-25): restrict the
legacy system, show that it is not as capable as it should be, simulate a
realistic environment, and let only simple traffic in and out.

The harness is plain Python run through Poetry (no Docker or VMs, as the group
decided). `sensor.py` and `test_sensor.py` are unchanged. It replaces the
earlier attempt (closed PR #2), which was a test suite rather than a simulated
device.

### Prompt 1

The prompt below was itself written with the LLM, from the group's harness
notes, the rejected PR #2 and hekazu's review of PR 1. The group had ruled
out Docker. The earlier requirement to demonstrate ML-KEM was also dropped,
as that comes later.

> This repo is a university group project (Software Development, Maintenance and Operations). The course task: build a legacy system that runs on **simulated limited hardware**, and later modernise it. All code must be LLM-generated and reviewed (see CONTRIBUTING.md).
>
> The legacy app is `sensor.py`: a sauna sensor that returns random temperature and humidity values over plain HTTP at `GET /health`, `GET /` and `GET /measurements` (spec: `documentation/sensor-interface.md` on `origin/main`). It uses only the standard library. PR 1 is still under review and its author is changing it, so **do not modify `sensor.py` or `test_sensor.py`**. Depend only on `create_server(host, port)` and the HTTP interface, not on internals.
>
> ## What "harness" means here
>
> The harness is the **simulated constrained device** that the legacy sensor runs inside. It is not a test suite. A previous attempt (branch `pypaa/test-harness`, closed PR #2) built characterization tests, a fault proxy and a latency baseline, and was rejected because it did not simulate the environment. Do not reuse it.
>
> Goals from the group meeting (documentation/meetings/meeting-03.md):
>
> - Restrict the legacy system.
> - Show that it is not as capable as it should be.
> - Realistic: simulate the environment the sensor would be seeing.
> - No interaction with anything else, but allow simple traffic to pass through and get a response from within.
>
> ## Requirements
>
> **No Docker, no VMs.** The group decided these are too heavy. Everything is Python, run through Poetry (`poetry run ...`). Prefer the standard library. Add a third-party dependency only if the stdlib really cannot do the job, and justify it.
>
> 1. **Run the sensor as a restricted child process (the "device").** A launcher starts the sensor in its own Python process and applies OS-enforced limits wherever the OS allows it:
>    - a memory cap and a CPU cap. 

>    Say clearly which limits the OS enforces and which the Python sandbox only emulates. The sandbox is a simulation, not a security boundary, and the README must say so.
> 2. **Isolate the network behind a "link".** The sensor binds only to loopback on an internal port. A small link process is the single public entry point, on localhost. 

> 3. **Make the environment realistic.** Model the conditions a cheap sauna controller would live with, through the device's hardware limits and its network link.

> 4. **Show that it is not as capable as it should be.** Add a report command that **measures** the device under the profile and compares it with the same sensor run unrestricted:
>    - throughput, latency and peak memory
>    - a list of capabilities the device lacks, each proven by actually attempting it (an outbound connection, a file write, importing a blocked module)
>    Nothing may be hard-coded or faked. Leave ML-KEM and crypto out entirely. That comes later.

> 5. **Put all limits in one profile file.** This covers the memory and CPU caps, the link bandwidth, latency, jitter and drop rate, and the module allowlist. Use TOML read with `tomllib`. Next to each value, note which kind of real device it imitates.
>
> ## Constraints
>
> - Keep it small and easy for group members to review: a few plain modules, no frameworks, short functions. Size matters. The rejected attempt was about 2,000 lines.
> - One command to start the device together with its link, and one for the report, e.g. `poetry run python -m harness up` / `... report`. Ctrl+C must stop everything, with no orphaned processes.
> - No hard-coded ports. Localhost only.

### Results 1

The LLM skipped the separate plan step and wrote the files listed under
Purpose, about 800 lines in total including the profile and the tests.

Checks it ran:

* Windows 11, Python 3.14: `poetry run pytest` gave 17 passed (9 harness
  checks + the 8 existing sensor tests). `python -m unittest test_sensor.py`
  still passes.
* Linux (Docker containers, used only for testing): Python 3.12, 3.13 and 3.14
  gave 16 passed, 1 skipped. The CPU check is skipped because the containers
  have no systemd, so Linux had no CPU cap there. The systemd path is
  untested.
* `python -m harness report` on Windows: the fixed CPU task took 1.80 s on
  the device against 0.21 s unrestricted. The device was reached through the
  link at about 3 requests/s, with a median of about 350 ms. All five other
  capabilities were blocked on the device and worked unrestricted.
* Force-killing the harness also killed the device on Windows (Job Object).

Things found while building it:

* The first allowlist, recorded on Windows only, broke the device on Linux.
  Linux loads fewer modules at start-up (for example `re`), and Python 3.12's
  `random` needs `_sha2`. The allowlist is now recorded on 3.12-3.14 on both
  operating systems.
* Answering a sensor request costs too little CPU for the 10 % cap to show in
  the request numbers, so a timed CPU probe was added to show the cap
  directly.
* On Windows, `Popen.wait()` cannot be interrupted by Ctrl+C, so `up` polls
  instead. Ctrl+C could not be tested automatically; please try it by hand.

Known limitations are listed in `harness/README.md`.
