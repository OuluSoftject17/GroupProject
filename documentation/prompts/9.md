# PR-9

## Purpose

Upgrade the webedge from RSA to ML-KEM key establishment, so that the
client–webedge connection is protected against quantum attackers. The
webedge publishes an ML-KEM-768 public key. The client uses it to agree a
shared secret, and both directions are then encrypted with AES-256-GCM.

The webedge keys are loaded from files, so they survive restarts and clients
can pin the public key. This protects against a man-in-the-middle who swaps
the key.

This PR builds on PR #6 (`ranjeet/webedge`). It changes `webedge.py`,
`test_webedge.py` and `.gitignore`, and adds
`documentation/webedge-keys.md`.

### Results 1

The LLM implemented everything the prompt asked for. Changes to `webedge.py`:

* An ML-KEM-768 key pair is generated at startup, next to the RSA key.
* `GET /kem-public-key` returns the public key (base64) and `GET /metrics`
  returns the counts as JSON, for example
  `{"rsa": {"200": 1}, "mlkem": {"200": 2, "400": 1}}`.
* The `X-Key-Exchange` header chooses `mlkem` or `rsa`. Without the header,
  RSA is used, so legacy clients do not need to change.
* `WEBEDGE_ALLOW_RSA=false` rejects RSA requests with 403.
* Errors go through a small `RequestError` class. All invalid input returns
  400 "Invalid encrypted request" without exception details. A response too
  large for RSA now returns 500 instead of crashing the handler.
* Each request is logged as one line, for example
  `key_exchange=mlkem status=200 path='/test'`. Keys and bodies are never
  logged.

`test_webedge.py` got 15 new tests. The client side of ML-KEM in the tests is
written separately from `webedge.py`, so the tests check that both sides
agree on the protocol.

Beyond the prompt, the LLM made these changes and explained each of them:

* **Path check (security fix).** The decrypted path must start with `/`.
  Before, a path such as `@evil.example/` turned the target URL into
  `http://localhost:8001@evil.example/`, so anyone could make the webedge
  request any host. The webedge public key is public, so any outsider could
  do this. A test was added.
* A client key that is valid but not RSA (for example an EC key) now returns
  400. Before, the handler crashed.
* A `Content-Length` of 0 or less now returns 400. A negative value made
  `rfile.read(-1)` wait for the connection to close.
* The tests use `127.0.0.1` instead of `localhost`. On Windows every
  connection to `localhost` first waited about 2 seconds for IPv6. The 5
  original tests took 13 s; all 20 tests now take about 1 s.
* The test servers are closed in `tearDownClass`, and the two original
  400-error tests use a new `assert_status` helper that closes the error.
  This removed all `ResourceWarning`s.

The LLM also found and fixed two problems in its own first version:

* It logged each request after sending the response. The log test could
  then finish before the server thread wrote the log line. Logging was moved
  before the response.
* It wrote the files with LF line endings, while the repository uses CRLF.
  Git then showed every line as changed. The files were converted back.

Design decisions the LLM explained:

* **ML-KEM-768 instead of 1024.** 768 is NIST security category 3 (about
  AES-192). It is the common default, also used in the hybrid X25519MLKEM768
  for TLS, and its ciphertext (1088 bytes) still fits in an HTTP header.
* **ML-KEM with AES-256-GCM.** ML-KEM only agrees a 32-byte secret. AES-GCM
  encrypts the data, detects tampering and has no size limit, which removes
  the 190-byte RSA limit.
* **HKDF without salt, `info=b"webedge-mlkem-v1"`.** The ML-KEM secret is
  already uniformly random, so a salt adds nothing. The `info` label ties
  the key to this protocol version.
* **Random 12-byte nonces.** Every request has its own key, and each key
  encrypts only two messages, so random nonces are safe.
* **Tampered KEM ciphertexts.** ML-KEM does not report an error for a
  changed ciphertext. It returns a different secret (implicit rejection), so
  the error appears as an AES-GCM `InvalidTag`. The LLM checked this before
  writing the code, and there is a test for it.
* **403 when RSA is disabled.** The request is understood but refused by
  policy. 426 Upgrade Required was considered, but it formally requires an
  `Upgrade` header.

Checks it ran (Windows 11, Python 3.14):

* `poetry run python -m unittest test_webedge.py` gave 20 tests OK, also
  with `-W error::ResourceWarning`.
* `poetry run pytest` gave 28 passed.

Remaining risks, as listed by the LLM:

1. The webedge public key is not authenticated. A man-in-the-middle can
   replace the key returned by `/kem-public-key` and read all traffic. This
   needs key pinning, pre-distributed keys or a signature (for example
   ML-DSA). This is the largest remaining gap.
2. While RSA is allowed, an attacker can remove `X-Key-Exchange` and force
   RSA, which is open to "harvest now, decrypt later". Only
   `WEBEDGE_ALLOW_RSA=false` prevents this.
3. Keys are generated again on every restart. There is no key rotation, and
   RSA clients that stored the old key stop working.
4. ML-KEM is used alone, not as a hybrid with X25519 as in TLS. If ML-KEM or
   its implementation turned out to be weak, there is no classical layer
   left.
5. There is no replay protection. A captured request can be sent again. For
   read-only GET requests the impact is low.
6. Metadata is not encrypted: the method header, the target's
   `Content-Type`, the response size and timing are visible over plain
   HTTP. `/metrics` and `/kem-public-key` have no authentication.
7. There is no limit on the request size, so a large `Content-Length` can
   use up memory.
8. Error codes from the target, such as 404, are returned as 502, because
   `HTTPError` is a subclass of `URLError`. This was already the case before
   this PR.
9. A GET request with a body is unusual, and some proxies drop such bodies.
10. The ML-KEM implementation in `cryptography`/OpenSSL is trusted. The tests
    only check that it works together, not that it is correct.

### Results 2

Before choosing a file format, the LLM checked the library. `cryptography`
50.0.2 can store ML-KEM private keys as PKCS#8 PEM, PKCS#8 DER or the raw
64-byte seed. `load_pem_private_key()` loads a PKCS#8 PEM file as an
`MLKEM768PrivateKey`, and a corrupt file raises `ValueError`.

Changes to `webedge.py`:

* `load_keys()` loads the private keys from `WEBEDGE_KEM_KEY_FILE` and
  `WEBEDGE_RSA_KEY_FILE`. It loads and checks both keys before replacing
  anything, so a failure never leaves one old and one new key.
* `run()` calls `load_keys()`. If a key file is missing, corrupt or holds
  the wrong type of key, WebEdge stops with
  `Webedge refusing to start: ...` and exit code 1. If a variable is not
  set, it logs a warning and uses a temporary key.
* At startup, the ML-KEM fingerprint is logged (the SHA-256 of the raw
  public key bytes, in hex).
* `python webedge.py generate-keys <directory>` writes the key files and
  prints the fingerprint. It refuses to overwrite existing files, and creates
  the private key files with permissions `0600` on POSIX.

`.gitignore` now ignores `keys/` and `*-private.pem`. The guide
`documentation/webedge-keys.md` explains how to generate keys, give the
public key or fingerprint to clients, pass the key files to WebEdge, and
rotate keys by hand.

`test_webedge.py` got 13 new tests. They check that:

* the generated key files load back to the same keys;
* a client with the pinned key still works after a simulated restart;
* missing, corrupt and wrong-type key files fail, and WebEdge refuses to
  start;
* the temporary key causes a warning, and the fingerprint is logged without
  any private key;
* `generate-keys` refuses to overwrite files, and the private key files are
  `0600` on POSIX;
* a man-in-the-middle test: a fake server serves an attacker's key, and the
  client that pins the real fingerprint rejects it;
* a request built against an attacker's key is rejected by WebEdge with 400.

Beyond the prompt, the LLM:

* also wrote `webedge-rsa-public.pem`, because legacy clients now need the
  RSA public key in the same way;
* added a test that WebEdge really refuses to start with a bad key file,
  not only that loading fails;
* added a short "Future work" section to the guide, because the constraints
  asked for signing, TLS and automatic rotation to be mentioned as future
  work.

Design decisions the LLM explained:

* **PKCS#8 PEM for both keys.** The file says which type of key it holds,
  so one loader works for both keys and a wrong-type file is detected. The
  raw seed was rejected because it has no type information: any 64 bytes
  would load.
* **Fingerprint over the raw public key bytes, not the PEM file.** These
  are the bytes that `/kem-public-key` serves, and differences in PEM
  formatting or line endings cannot change the fingerprint.
* **Fail when configured, warn when not.** A configured key that fails to
  load would otherwise quietly break every pinned client, while the operator
  believes pinning is active. Without configuration it is development mode,
  so tests and local runs keep working.
* **Keys load in `run()`, not when the module is imported.** A bad file
  gives a clear message instead of an import error, and `generate-keys` and
  the tests are not affected.
* **Pinning instead of signing.** With signing, clients still have to trust
  a signing key they received in advance. For one server, pinning its key
  directly gives the same security without ML-DSA or certificates.
